# Hippocampus 初始实施计划

> 本文是历史初始规划，仅供参考；当前行为以 README、`config.toml` 和实际 CLI 为准。

## 1. 项目目标

Hippocampus 是一个面向日常长期对话的外部上下文管理系统。模型本身不承担持久化记忆，系统负责保存完整对话、检索历史证据、控制上下文预算，并将可追溯的原文片段组装后交给本地 Ollama 模型。

第一阶段的目标不是一次性实现完整的“类人记忆”，而是建立一条可运行、可观察、可逐步扩展的最小链路：用户发送消息后，系统保存原文、获取最近对话、按照预算组装上下文、调用 Qwen 生成回复，并记录本轮实际使用了哪些上下文。

## 2. 核心原则

- 原始对话是唯一事实来源，采用追加写入方式保存，不用摘要替代或覆盖原文。
- 索引、实体、事件、关系和状态都是可重建的派生数据，必须能够追溯到原始事件或原文片段。
- 上下文组装和长期检索分离。组装器只负责预算与排布，检索器负责提供候选证据。
- 每次检索和组装都应可解释，能够查看候选来源、排名、选择原因和丢弃原因。
- 先建立简单可靠的基线，再增加 embedding、时间推理、事件切分和关联图。

## 3. 初始技术方向

- 主要语言：Rust。
- 模型服务：本地 Ollama，测试模型为 Qwen3.5 9B。
- 原始数据：raw session JSON 是唯一事实；SQLite（WAL）包含不可变巩固 audit ledger 与可重建 projection，HNSW 可重建。
- 关键词检索：SQLite FTS5，补充中文字符 n-gram 索引。
- 向量检索：在关键词基线稳定后接入 HNSW 或 FAISS。
- 图计算：初期使用 SQLite 关系表和稀疏矩阵；达到规模瓶颈后再考虑 Rust 实现。
- 接口层：先提供简单的 Rust API 或本地 HTTP API，不在初期拆分多个微服务。
- 测试与评测：cargo test、自建对话用例，之后接入 LongMemEval 和 LoCoMo。

## 4. 建议的模块边界

项目初期应保持模块少而清晰，至少包含以下职责：

- 事件存储：保存会话、用户消息、模型回复和原文片段。
- 上下文组装：管理系统提示、当前消息、最近对话、历史证据和输出预留预算。
- 检索：提供统一候选结果，逐步实现 BM25、向量、实体、时间和图检索。
- 模型适配：封装 Ollama 调用，不让业务逻辑依赖具体模型接口。
- 后台巩固：异步更新索引和关联关系，不修改原始事件。
- 评测：分别测试证据召回、上下文质量和最终回答质量。
- 追踪日志：记录每轮候选、排序、token 使用、最终上下文和各阶段延迟。

模块之间应通过稳定的数据结构交互。检索结果至少要携带原始事件 ID、原文范围、时间、角色、检索通道、分数和选择原因。

## 5. 分阶段实施

### 阶段一：最小对话链路与上下文组装器

首先完成最简单的上下文组装器，只处理系统提示、当前用户消息和最近对话，不接入长期检索。

主要工作：

- 实现 Ollama 客户端和基本对话入口。
- 建立可配置的上下文总预算、输出预留和安全余量。
- 从最新消息开始反向选择最近对话，再按时间正序放入最终上下文。
- 对超长消息只选择有明确偏移量的原文片段，不修改存储中的完整原文。
- 保存每轮最终发给模型的上下文清单和 token 使用情况。

验收标准：

- 能与本地 Qwen 完成连续多轮对话。
- 上下文不会超过配置预算。
- 最近消息的排列顺序正确。
- 可以准确查看本轮哪些消息被加入或因预算不足被舍弃。

### 阶段二：不可变原始事件存储

在最小链路可运行后，正式建立长期数据模型。至少需要会话、事件、原文片段、上下文运行记录和检索命中记录。

原始事件需要记录会话、顺序、角色、创建时间、完整文本、回复关系、内容哈希和 token 数。原文片段只保存事件引用及字符偏移，不单独生成改写文本。

验收标准：

- 所有用户消息和模型回复都能完整回放。
- 删除或修改派生索引后，可以从权威会话 JSON 重新建立。
- 每次回答都能追溯到当时使用的上下文和原始事件。

### 阶段三：BM25 长期记忆 MVP

首先使用 FTS5、中文分词字段和字符 n-gram 建立关键词检索，不急于接入 embedding。

主要工作：

- 对消息级和原文片段级内容建立全文索引。
- 排除当前消息、重复候选和已经出现在最近对话中的内容。
- 检索到目标片段后，按独立预算补充少量前后文或回复链。
- 将长期证据作为独立区域交给上下文组装器。
- 记录 BM25 分数、候选排名和最终选择原因。

验收标准：

- 能从大量无关消息中找回很早以前出现的姓名、地点、日期、偏好和明确事实。
- 最终提供给 Qwen 的内容是原文而不是生成摘要。
- 从错误回答可以定位到检索、选择或生成中的具体阶段。

完成本阶段后，系统形成第一个可用 MVP。

### 阶段四：Embedding 与混合检索

在 BM25 基线可复现后增加语义召回。BM25 和 embedding 应并行工作，而不是互相替代。

主要工作：

- 为原文片段建立向量索引，并始终保留到原始片段 ID 的映射。
- 分别召回 BM25 和向量候选，使用 RRF 进行初始融合。
- 使用去重和多样性策略，避免相似候选占满上下文。
- 对比关键词、向量和混合检索的召回率、延迟与 token 成本。

验收标准：

- 改写后的问题能够找回没有明显关键词重合的历史记录。
- 人名、数字和日期类精确检索不因加入 embedding 而退化。
- 混合检索相较单一检索通道有可测量的收益。

### 阶段五：事件切分与多粒度记忆

在消息级检索稳定后，将连续对话组织为原文片段、消息、事件和会话等多种粒度。不同粒度只保存范围和成员关系，不复制或重写原始内容。

初期可以根据时间间隔、人物、地点、显式话题转换和 embedding 主题变化确定事件边界。精确事实优先返回片段或消息，跨阶段问题则优先检索事件或会话，再展开其中的原文证据。

验收标准：

- 精确问题不会因为事件过大而引入过多无关文本。
- “上次讨论的事情”一类问题能够恢复相对完整的情景。
- 不同粒度的检索效果可以单独评测和比较。

### 阶段六：时间、状态与冲突

引入提及时间、事件时间、有效起点和有效终点，保留信息的完整演化历史。新信息只能使旧状态失效或被替代，不能覆盖原始记录。

第一版优先支持明确的时间表达、显式纠正、否定变化和同一属性的新旧值。检索时可以同时提供新旧原文，但要标记时间和可能的失效状态。

验收标准：

- 能区分“以前是什么”和“现在是什么”。
- 用户更新偏好或地址后，不会继续把旧记录当作当前事实。
- 冲突判断能够回溯到双方的原始证据。

### 阶段七：离线关联图

最后增加海马体式联想。后台任务只建立派生关系，包括回复、共享实体、时间邻近、关键词共现、embedding mutual top-k、共同召回、支持、冲突和替代关系。

在线检索使用 BM25 和 embedding 结果作为种子，限制在一至两跳内进行关联扩散，并通过 Personalized PageRank 或类似算法排序。图检索必须有单独候选上限和 token 预算，避免联想范围失控。

验收标准：

- 能找回措辞不相似但通过人物、事件或因果链相关的记录。
- 图召回结果都能解释关联路径并映射回原文。
- 加入图检索后，多跳问题得到提升，简单事实检索不明显退化。

### 阶段八：自适应上下文预算与产品化

在所有基础检索通道稳定后，根据问题类型动态分配最近对话、精确证据、事件上下文和关联证据的预算。初期使用规则即可，不需要额外 LLM 进行查询总结。

同时补充对话人物实体/状态隔离、逻辑删除、索引重建、配置版本、故障恢复、隐私控制和长期运行监控；这里的隔离不包含 account/auth/multitenancy。

## 6. 评测计划

评测必须与实现同步进行，并区分检索质量和最终回答质量。

初期应建立一组小型、可重复的人工测试对话，覆盖久远事实、问题改写、昵称、日期、数字、偏好更新、事实冲突、多跳关系、无答案拒答、相似干扰、历史错误回复和历史提示注入。

检索层重点关注：

- Evidence Recall@5 和 Recall@10。
- MRR 和正确证据排名。
- 单位 token 内的有效证据数量。
- 旧状态误召回率和无答案错误召回率。
- 各检索通道的延迟。

回答层重点关注：

- 最终答案正确率。
- 时间版本和冲突选择正确率。
- 没有证据时是否编造。
- 是否被历史 assistant 错误或历史提示注入影响。
- 输入 token、生成延迟和资源使用。

基础链路稳定后，再接入 LongMemEval、LoCoMo 以及测试隐式约束的扩展数据集。所有方法必须在相同模型、数据、预算和评测流程下比较。

## 7. 初始任务清单

建议从以下任务开始，按顺序完成：

1. 建立 Rust 项目骨架、配置管理和基础测试。
2. 实现 Ollama 客户端以及单轮、连续多轮调用。
3. 定义事件、原文片段、检索候选和上下文清单的数据结构。
4. 实现最近对话上下文组装器与 token 预算。
5. 建立 authoritative session JSON 和完整对话回放，并在 SQLite 保存 immutable audit ledger 与 projection。
6. 实现上下文 trace，记录选择和丢弃原因。
7. 编写第一批人工长期对话测试用例。
8. 接入 FTS5/BM25，形成长期记忆 MVP。

## 8. 初期暂缓事项

在 BM25 长期记忆 MVP 完成前，暂不投入以下工作：

- 不引入 Neo4j 等独立图数据库。
- 不拆分微服务。
- 不同时维护 Rust 和 C++ 两套实现。
- 不使用 LLM 摘要替代原始记录。
- 不训练复杂 reranker 或记忆策略模型。
- 不提前实现情绪、人格和重要性等难以客观评测的记忆类型。
- 不根据第三方项目公布的单一 benchmark 分数做架构决策。

## 9. MVP 完成定义

当系统满足以下条件时，可以认为初始 MVP 完成：

- 用户能够与本地 Qwen 进行持续多轮对话。
- 所有消息都以不可变原始事件保存。
- 系统能够通过 BM25 从很久以前找回相关原文。
- 上下文组装始终遵守 token 预算。
- 注入模型的每段历史证据都能追溯到原始事件和原文范围。
- 每次回答都能查看完整的检索和上下文组装过程。
- 已有自动化用例验证久远事实、干扰信息、无答案和事实更新等基本场景。

完成这一里程碑后，再按照 embedding、多粒度事件、时间冲突和关联图的顺序继续迭代。
